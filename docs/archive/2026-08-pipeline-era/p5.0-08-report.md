## 2. Implementation

### Endpoints

All eight, mounted under the repo's `/api/v1/...` convention, following the `context.ts` / `projects.ts` idiom — `export default async function memoryRoutes(fastify: FastifyInstance)`, a named-key response envelope, `reply.code()` for non-200.

| Method | Path | Success | Response |
| :-- | :-- | :-- | :-- |
| POST | `/api/v1/projects/:id/memory/decisions` | 201 | `{ decision }` |
| GET | `/api/v1/projects/:id/memory/decisions?status=` | 200 | `{ decisions }` |
| POST | `/api/v1/projects/:id/memory/decisions/:decisionId/supersede` | 201 | `{ decision }` |
| GET | `/api/v1/projects/:id/memory/briefing` | 200 | `{ briefing }` |
| POST | `/api/v1/projects/:id/memory/intents` | 201 | `{ intent }` |
| GET | `/api/v1/projects/:id/memory/intents/active` | 200 | `{ intent }` (`null` when unset) |
| POST | `/api/v1/projects/:id/memory/rules` | 201 | `{ rule }` |
| GET | `/api/v1/projects/:id/memory/rules` | 200 | `{ rules }` |

`projectId` always comes from the path, never the body — a `projectId` in the request body is overwritten by the path parameter (`{ ...body, projectId: id }`, spread first so the path wins). This is asserted in the tests. It removes a whole class of confusion where the URL says one project and the payload says another.

### Thinness

Zero SQL and zero lifecycle logic in the handlers. Each one destructures params, checks that the fields HTTP itself requires are present, calls exactly one `projectMemoryService` method, and sets a status code. The only non-trivial logic in the file is the error translator, which is an HTTP concern by definition.

Input checking is split deliberately:

- **The route checks presence** — `title`/`summary`/`rationale`, `goal`, `title`/`statement` — because a request missing a required field is a malformed request, and answering 400 with a field list is better than surfacing the service's internal exception text.
- **The route checks the `status` query parameter** against `DECISION_STATUSES`, because `listDecisions` accepts any string and silently returns an empty list. `?status=active` would look like "this project has no active decisions" instead of "that is not a status". Now it is a 400 naming the four valid values.
- **The service checks everything else** — enum membership on write, confidence clamping, cross-project supersede, referential integrity. The route does not duplicate any of it; it translates the resulting throw.

### Error translation

One module-level function maps a thrown error onto a status code, so no handler branches on error text:

| Condition | Status | Rationale |
| :-- | :-- | :-- |
| message ends in `not found` | 404 | a decision id that resolves to nothing |
| message contains `FOREIGN KEY constraint failed` | 404 | `project_id` references `projects(id)`; an unknown project fails the constraint. Verified: `node:sqlite` throws `Error` with this message and `errcode: 787` |
| message starts with `[ProjectMemoryService]` | 400 | everything the service rejects deliberately — missing text, unrecognised enum, cross-project supersede |
| anything else | 500 | unclassified |

Two status choices worth stating because they are judgement calls, not defaults:

- **`GET /memory/intents/active` returns `200 { intent: null }`, not 404, when no intent is set.** The resource — "this project's current intent" — exists and its value is "none". A 404 would force every client to distinguish "no intent" from "no such route".
- **`GET` on an unknown project returns `200` with an empty collection**, not 404. The route delegates entirely to the service, which scopes by `project_id` and legitimately finds nothing. Making this a 404 would require the route to query `projectManager` — business logic the brief explicitly excludes. See § 5 item 2.

### Server registration

`index.ts` gained three additive lines inside `start()`: the import, `await fastify.register(memoryRoutes)` after `contextRoutes`, and `projectMemoryService.initEventBusListeners()` immediately before `fastify.listen()` — so subscriptions are in place before the server accepts any request that could publish a memory event.

**This registration also closes a caveat carried since P5.0-04.** `tsup` bundles from `src/index.ts`; until now nothing imported `ProjectMemoryService`, so `pnpm run build` succeeded without ever compiling it. `index.ts` now imports it, and the bundle grew from 543 KB to 568 KB with 29 references to the memory service and its tables. The build is finally real evidence for this code.

## 5. Remaining issues and questions

**1. `request: any` in every handler — 8 lint warnings.** This is the established idiom in all eleven existing route files (`context.ts`, `projects.ts`, `git.ts`, …), and `CLAUDE.md` directs new code to read like the surrounding code. Fastify's route generics (`fastify.post<{ Params: { id: string }; Body: CreateDecisionInput }>`) would give real typing on `params`/`body` and drop the warnings, but would make this the only route file in the repo written that way. I chose consistency. Worth a repo-wide decision rather than a one-file exception.

**2. `GET` on a non-existent project returns 200 with an empty collection.** Consistent with delegating entirely to the service, and it means a client cannot distinguish "project deleted" from "project has no rules yet". Adding a `projectManager.getProject(id)` existence check would fix it at the cost of the thinness rule the brief sets. Note that P5.0-01 established `sessions`/`approvals` have no FK to `projects`, so a *deleted* project can still return non-empty `recentAgentWork` from `/memory/briefing` — a briefing for a project that no longer exists.

**3. The cross-project supersede 400 leaks another project's id.** The service message is `Cannot supersede a decision across projects: <decisionId> belongs to <otherProjectId>, not <requestedProjectId>` and the route returns it verbatim. A caller can therefore probe decision ids and learn which project owns one. Once memory is exposed to a multi-user workspace this is an information disclosure. Either return a generic 404 (treating "not in this project" as "not found", which is also the more RESTful reading), or strip the owning project id from the message.

**4. No authorization beyond the global auth middleware.** `authMiddleware` runs on all `/api/v1/` routes, but it falls back to a `defaultDevUser` whenever `NODE_ENV !== 'production'`, and these routes apply no `rbacGuard` or `entitlementGuard`. Any paired device can read and write any project's memory. This matches `projects.ts` and `context.ts`, so it is a subsystem-wide gap rather than one introduced here — but memory is the first thing that will contain durable, sensitive project reasoning.

**5. No Fastify schemas.** No `schema: { body, params, response }` on any route, so there is no automatic validation, no serialization fast path, and no generated API documentation. Again consistent with the rest of the repo; noted because a REST surface is exactly where schemas pay off.

**6. No pagination or limits on the list endpoints.** `GET /memory/decisions` and `GET /memory/rules` return everything, and `/memory/briefing` inherits the unbounded `activeDecisions` / `architecturalRules` problem from P5.0-06 § 5 item 1. That concern is now reachable over HTTP.

**7. `initEventBusListeners()` is called at startup but still registers nothing** (P5.0-07 § 5 item 1). The seam is wired; what it should subscribe to remains a product decision. Relatedly, `memory.*` events are still not forwarded to clients — `socketManager` broadcasts specific types to project rooms and `memory.*` is not among them, so a dashboard cannot react live to a decision recorded via REST.

**8. Carried forward unresolved.** The bidirectional `supersededBy` (P5.0-05 § 5.1) is now on the wire: `POST …/supersede` returns a decision whose `supersededBy` points at the decision it *replaced*, while the same field on the superseded decision points at its *replacement*. Two opposite meanings in one documented field, now part of a public API contract. Also open: `relatedFiles` has no column (P5.0-04 § 5.1), `scope_pattern` `'*'` vs `'**'` (P5.0-03 § 5.3), no `CHECK` constraints on enum columns.

**9. The Blueprint still has no Project Memory entry, and CI is still red on `main`** (38 pre-existing lint errors). Eight tasks in, the subsystem is complete end to end — schema, service, lifecycle, briefing, events, REST — and the normative specification still does not describe any of it. `CLAUDE.md` states the Blueprint governs and that spec changes require a Change Proposal from `.agents/templates/`. **This is now the largest outstanding item in the phase**, and it is documentation work, not code.
