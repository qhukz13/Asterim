## 1. Project identity compatibility

**Confirmed compatible.**

`DatabaseService.ts:42-50`:

```sql
CREATE TABLE IF NOT EXISTS projects (
  id TEXT PRIMARY KEY,
  workspace_id TEXT,
  name TEXT NOT NULL,
  path TEXT NOT NULL,
  visibility TEXT NOT NULL DEFAULT 'private',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY(workspace_id) REFERENCES workspaces(id) ON DELETE SET NULL
);
```

- `projects.id` is `TEXT PRIMARY KEY`, populated by `crypto.randomUUID()` (`ProjectManager.ts:72`). It is a plain UUID string with **no prefix** — unlike `environment_project_attachments.id`, which is prefixed `epa_` (`ProjectManager.ts:84`). Memory tables must store the bare UUID.
- `workspace_id` is a **separate, nullable** column and is *not* an identity for the project. It may be `NULL` or `''` for personal-workspace projects (`ProjectManager.ts:33`). Memory tables must key on `project_id`, never `workspace_id`.
- The established FK pattern for project-owned tables is `FOREIGN KEY(project_id) REFERENCES projects(id) ON DELETE CASCADE` (used by `threads`, `events`, `contexts`, `context_entries`, `environment_project_attachments`). Phase 5.0 memory tables should follow this exactly.
- `node:sqlite`'s `DatabaseSync` enables foreign-key enforcement by default and the codebase issues no `PRAGMA foreign_keys` override, so `ON DELETE CASCADE` will actually fire on project deletion (`ProjectManager.removeProject`, line 96-100, is a bare `DELETE FROM projects` and relies entirely on cascade).

**Type contract:** `ProjectConfig.id: string` (`ProjectManager.ts:5`), and `AsterimEvent.payload` carries optional `projectId?: string` / `threadId?: string` (`packages/shared/src/events.ts:6`). A `projectId: string` field on any new memory payload type is consistent with the existing shared contract.

## 2. Agent session & approval querying capability

**Confirmed sufficient — no `agent_work_records` table is needed.** Both tables already exist with the required columns, but three gaps must be designed around.

### `sessions` (`DatabaseService.ts:76-85`)

| Column | Type | Notes for `getProjectBriefing()` |
| :-- | :-- | :-- |
| `id` | TEXT PK | UUID |
| `project_id` | TEXT NOT NULL | **No FK declared** (see gaps) |
| `thread_id` | TEXT | Added via `ALTER TABLE`, so may be `NULL` on legacy rows |
| `agent_type` | TEXT NOT NULL | `'aider' \| 'claude' \| 'antigravity'` |
| `status` | TEXT NOT NULL | `'running' \| 'stopped' \| 'exited' \| 'crashed'` |
| `pid` | INTEGER | nullable |
| `started_at` | INTEGER NOT NULL | `Date.now()` ms epoch |
| `updated_at` | INTEGER NOT NULL | `Date.now()` ms epoch |

Write sites are complete and consistent: insert on start (`AgentService.ts:325-337`), `status`/`updated_at` update on exit/crash (`:249-252`), on user stop (`:416-417`), and on server-restart recovery where orphaned `running` rows are swept to `crashed` (`:455-457`). This means `updated_at` is a reliable "last agent activity" timestamp and `status` is never left dangling across restarts.

A briefing query such as
`SELECT agent_type, status, started_at, updated_at FROM sessions WHERE project_id = ? ORDER BY started_at DESC LIMIT n`
is fully supported today.

### `approvals` (`DatabaseService.ts:86-95`)

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | TEXT PK | UUID |
| `project_id` | TEXT NOT NULL | **No FK declared** |
| `thread_id` | TEXT | Added via `ALTER TABLE` — **never written** (see gaps) |
| `action_id` | TEXT NOT NULL UNIQUE | correlation id used by the client response |
| `description` | TEXT NOT NULL | human-readable intent |
| `command` | TEXT NOT NULL | the exact command the agent asked to run |
| `status` | TEXT NOT NULL | `'pending' \| 'approved' \| 'denied' \| 'expired'` |
| `created_at` | INTEGER NOT NULL | `Date.now()` ms epoch |

`ApprovalManager.requestApproval()` inserts (`:152-163`); the `client.approval_response` subscriber transitions `pending → approved/denied` (`:113-116`); the timeout path transitions `pending → expired` (`:177-180`). `command` + `description` + `status` + `created_at` is enough to render "what the agent recently asked to do and whether the user allowed it".

### Gaps to design around (not blockers)

1. **`approvals.thread_id` is dead.** The column exists but the only INSERT (`ApprovalManager.ts:153`) omits it, so every row has `thread_id = NULL`. A briefing can filter by `project_id` only; per-thread approval attribution is not available without a (separate, out-of-scope) fix to the INSERT.
2. **No resolution timestamp on `approvals`.** Only `created_at` exists; the approve/deny/expire updates do not stamp a time. "When was this decided" is unavailable — order and recency must be derived from `created_at`.
3. **No indexes on `sessions` or `approvals`.** Neither table has any index beyond its primary key (contrast `idx_events_project_timestamp` at `DatabaseService.ts:166-169`). Briefing queries filtering on `project_id` will full-scan. P5.0-02 should add `idx_sessions_project_started` and `idx_approvals_project_created` via the existing idempotent `CREATE INDEX IF NOT EXISTS` pattern — additive and safe for existing user databases.
4. **No FK on `sessions.project_id` / `approvals.project_id`.** Deleting a project leaves orphaned session and approval rows behind. Briefing queries should therefore join against `projects` (or tolerate orphans) rather than assume referential integrity. New memory tables should declare the FK properly and not inherit this omission.

### Richer alternative already available

`events` (`DatabaseService.ts:58-67`) stores every `AsterimEvent` with `project_id`, `thread_id`, `timestamp`, `type`, and `payload_json`, indexed by `idx_events_project_timestamp`. `type = 'chat.message'` rows are already queried this way for history detection (`AgentService.ts:220`). This is the correct source for narrative "what happened" content in a briefing; `sessions`/`approvals` supply the structured lifecycle and gate facts. Nothing here justifies a redundant `agent_work_records` table.

## 3. Test database initialization pattern

**There is no test infrastructure in this repository.** This is the single most consequential finding.

- No test runner is installed or configured anywhere: no `vitest`, `jest`, `node:test`, or `@testing-library` dependency; no `"test"` script in the root, `apps/server`, or `packages/shared` manifests; no test config file.
- No `*.test.ts` / `*.spec.ts` files exist. The `test-*.js` / `test_*.ts` files at the repo root and in `apps/*`, `packages/adapters` are ad-hoc debug scripts, not a suite, and are excluded from every build (`apps/server/tsconfig.json` includes only `src/**/*`).
- CI (`.github/workflows/ci.yml`) runs exactly `pnpm run lint` and `pnpm run build`. Nothing else.

### The isolation mechanism that *does* exist

`DatabaseService.resolveDataDir()` (`DatabaseService.ts:13-19`) resolves `process.env.ASTERIM_DATA_DIR` first and falls back to `path.join(os.homedir(), '.asterim')`. Setting `ASTERIM_DATA_DIR` to a temp directory is the only supported way to redirect the database away from `~/.asterim/asterim.db`.

Two constraints any future test harness must respect:

1. **Module-level singleton construction.** `export const dbService = new DatabaseService()` (`DatabaseService.ts:434`) runs the constructor — including `mkdirSync` and `init()` — at *import* time. `ASTERIM_DATA_DIR` must be set **before** the first import of `DatabaseService` or anything that transitively imports it (`ProjectManager`, `AgentService`, `ApprovalManager`, `socketManager`, …). A test file that sets the env var inside a `beforeAll` will already have polluted `~/.asterim`.
2. **No in-memory mode.** The path is unconditionally `path.join(dataDir, 'asterim.db')`, so `:memory:` cannot be passed. Isolation must be a real temp directory (e.g. `fs.mkdtempSync(path.join(os.tmpdir(), 'asterim-test-'))`), torn down after the run.

If P5.0 requires unit tests for `getProjectBriefing()`, standing up the runner and a temp-dir fixture is net-new work that must be scoped explicitly — it does not exist today.
