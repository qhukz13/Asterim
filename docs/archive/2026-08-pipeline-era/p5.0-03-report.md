## 2. DDL additions

### Write-Ahead Logging

Placed at the head of `init()`, before any DDL, so the journal mode is set once per database file:

```ts
try {
  this.db.exec('PRAGMA journal_mode = WAL;');
} catch {
  console.warn('[Database] Could not enable WAL journal mode; continuing with the default journal.');
}
```

The `try/catch` matches the defensive idiom already used throughout `init()`. WAL cannot be enabled on some network filesystems, and a data directory on an NFS/SMB mount (reachable via `ASTERIM_DATA_DIR`) would otherwise take the Core down at startup over a performance optimisation. On failure the database still opens in rollback-journal mode.

### Tables

Four tables, appended as a single `this.db.exec()` block after the existing auth-platform DDL, all exactly as specified in the brief:

| Table | Columns | Foreign keys |
| :-- | :-- | :-- |
| `project_decisions` | `id`, `project_id`, `title`, `summary`, `rationale`, `constraints_json` (default `'[]'`), `status` (default `'ACTIVE'`), `superseded_by`, `provenance` (default `'HUMAN_CONFIRMED'`), `confidence` REAL (default `1.0`), `created_at`, `updated_at` | `project_id → projects(id) ON DELETE CASCADE`; `superseded_by → project_decisions(id) ON DELETE SET NULL` (self-referencing) |
| `decision_code_refs` | `id`, `decision_id`, `file_path`, `symbol_name`, `commit_hash`, `created_at` | `decision_id → project_decisions(id) ON DELETE CASCADE` |
| `project_intents` | `id`, `project_id`, `goal`, `constraints_json` (default `'[]'`), `non_goals_json` (default `'[]'`), `status` (default `'ACTIVE'`), `created_at`, `updated_at` | `project_id → projects(id) ON DELETE CASCADE` |
| `architectural_rules` | `id`, `project_id`, `title`, `statement`, `severity` (default `'warning'`), `scope_pattern` (default `'*'`), `created_at` | `project_id → projects(id) ON DELETE CASCADE` |

This closes P5.0-01 blocker #5 for the new tables: unlike the pre-existing `sessions` and `approvals`, every memory table declares its `project_id` foreign key, so project deletion cannot leave orphaned memory rows.

The string columns map onto the `@asterim/shared` types from P5.0-02: `constraints_json` / `non_goals_json` hold the JSON encoding of `constraints: string[]` and `nonGoals: string[]`; `status`, `provenance`, and `severity` hold the `DecisionStatus`, `DecisionProvenance`, and `ArchitecturalRuleSeverity` literals. Serialization and validation are P5.0-04's responsibility — see § 5.

### Indexes

All seven, via `CREATE INDEX IF NOT EXISTS`:

```
idx_decisions_project_status   ON project_decisions(project_id, status)
idx_decision_refs_decision     ON decision_code_refs(decision_id)
idx_decision_refs_file         ON decision_code_refs(file_path)
idx_intents_project_status     ON project_intents(project_id, status)
idx_rules_project              ON architectural_rules(project_id)
idx_sessions_project_started   ON sessions(project_id, started_at)
idx_approvals_project_created  ON approvals(project_id, created_at)
```

The last two close P5.0-01 blocker #3: neither `sessions` nor `approvals` had any index beyond its primary key, so every `getProjectBriefing()` lookup would have full-scanned tables that grow with every agent start and every approval gate.

## 4. Side effect on the live development database

**The running dev server has already converted the real `~/.asterim/asterim.db` to WAL.** A `tsx watch` process (pid 185318, started 19:04:53) was listening on `:3000` before this session began. It hot-reloaded on the `DatabaseService.ts` edit, re-ran `init()`, and applied the pragma — `asterim.db-wal` and `asterim.db-shm` sidecar files appeared at 19:06, and a read-only probe of the real file confirms `journal_mode=wal`. The same restart regenerated `apps/server/pairing_pin.txt`, which is tracked by git and now shows as modified.

Nothing is lost — the integrity check above passes — but three consequences are worth stating:

1. **WAL is persistent in the database header.** Every future connection to that file uses WAL, including a build of the server from before this change. Reverting the commit does *not* revert the database. Undo requires `PRAGMA journal_mode = DELETE;` against the file.
2. **Two sidecar files now accompany the database.** Any backup, copy, or sync of `~/.asterim/asterim.db` must include `-wal` and `-shm`, or the most recent committed transactions can be lost. Copying the `.db` alone is no longer a complete backup.
3. **`apps/server/pairing_pin.txt` and `packages/shared/tsconfig.tsbuildinfo` are tracked build artifacts** that will ride along in the next commit unless checked out or gitignored.

## 5. Remaining issues and questions

**1. No `CHECK` constraints on the enum-like columns.** `status`, `provenance`, and `severity` accept any string at the database level; the `DecisionStatus` / `DecisionProvenance` / `ArchitecturalRuleSeverity` unions from P5.0-02 are compile-time only. Written to the brief's DDL exactly as specified, so this is intentional, but it means a bug in P5.0-04 could persist `'active'` where `'ACTIVE'` is expected and `idx_decisions_project_status` would silently partition on the bad value. Two options: add `CHECK (status IN (...))` constraints, or validate in the service layer. Note that adding a `CHECK` later is not possible via `ALTER TABLE` in SQLite — it needs a table rebuild — so if constraints are wanted, now is the cheap moment.

**2. `confidence` is unbounded.** `REAL NOT NULL DEFAULT 1.0` permits `-3` or `9.7`, while P5.0-02 documents the field as 0–1. Same trade-off and same timing constraint as above.

**3. `scope_pattern` defaults to `'*'`, but P5.0-02 documents `'**'` as the project-wide sentinel.** The brief specifies `'*'`; the shared type's doc comment says `'**'`. In glob semantics these differ — `*` conventionally does not cross path separators. One of the two should change before any rule row is written, or matching in P5.0-04 will disagree with the schema default. I did not alter the DDL, since it was given verbatim.

**4. No `updated_at` on `architectural_rules` or `decision_code_refs`.** Both are create-only per the brief. If rules ever become editable this needs a migration; the `ALTER TABLE … ADD COLUMN` pattern handles it, but a nullable column would then need a backfill.

**5. There is still no unit-test harness.** The verification script is deliberately named `temp_*` and is throwaway. If P5.0 wants durable coverage of memory persistence, standing up a runner remains net-new scope (P5.0-01 § 3). The env-var-before-import constraint the script demonstrates is the pattern any such harness must follow.

**6. The Blueprint still has no Project Memory entry.** Carried forward unresolved from P5.0-01 (§ 5, item 7) and P5.0-02 (§ 4, item 1). Schema is now physically in the codebase, which raises the stakes: the implementation has moved further ahead of the normative specification, and `CLAUDE.md` states the Blueprint governs. A Change Proposal against `ARCHITECTURE.md` / `DOMAIN_MODEL.md` should land before P5.0-04.
