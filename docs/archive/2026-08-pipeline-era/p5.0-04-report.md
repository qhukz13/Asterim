## 2. Implementation

### Structure

The service follows the row-interface + prepared-statement conventions of `ContextRepository.ts`: a private row interface per table, module-level mapper functions from snake_case row to camelCase domain type, and `dbService.getDb()` for every access. Persistence lives in the service itself rather than a separate repository, as the brief specifies.

Every SQL statement in the file is a prepared statement. The only string interpolation is the `IN (?, ?, …)` placeholder list in `attachCodeRefs`, which is built from `rows.map(() => '?')` — the count comes from the row array, never from caller input, and the ids are still bound as parameters.

### Methods

| Method | Behaviour |
| :-- | :-- |
| `createDecision(params)` | Validates input, generates a UUID, stamps `created_at`/`updated_at` with one `Date.now()`, inserts the decision and its code refs **inside a transaction**, then reads the record back. |
| `getDecision(id)` | Returns the decision with `codeRefs` attached, or `null`. |
| `listDecisions(projectId, filter?)` | `WHERE project_id = ?`, plus `AND status = ?` when `filter.status` is given, `ORDER BY created_at DESC`. Code refs attached for the whole batch. |
| `findRelevantDecisions(projectId, filePath)` | `JOIN decision_code_refs` on `project_id = ? AND file_path = ? AND status = 'ACTIVE'`, `SELECT DISTINCT`, newest first. |
| `getCodeRefs(decisionId)` | Code refs for a decision, oldest first. |
| `createIntent(params)` | Archives the project's `ACTIVE` intent and inserts the new one **in a single transaction**. |
| `getIntent(id)` | Intent by id, or `null`. |
| `getActiveIntent(projectId)` | `WHERE project_id = ? AND status = 'ACTIVE' ORDER BY created_at DESC LIMIT 1`. |
| `createRule(params)` | Inserts a rule; single statement, no transaction needed. |
| `getRule(id)` | Rule by id, or `null`. |
| `listRules(projectId)` | `WHERE project_id = ? ORDER BY created_at DESC`. |

`getCodeRefs`, `getIntent`, and `getRule` are additions beyond the brief's list. They exist because every `create*` method reads its record back before returning, which guarantees the caller sees exactly what was persisted (defaults applied, JSON round-tripped) rather than an optimistic in-memory reconstruction.

### Data handling decisions

**Transactions.** A private `transaction(fn)` helper wraps `BEGIN` / `COMMIT` / `ROLLBACK`. `createDecision` and `createIntent` use it, so a decision is never persisted with a partial set of code refs, and a project can never be left with two `ACTIVE` intents or none. The rollback path swallows a secondary `ROLLBACK` failure and rethrows the original error, so the real cause is never masked. It is **not** re-entrant — SQLite has no nested `BEGIN`; see § 5.

**Enum validation.** P5.0-03 recorded that the schema has no `CHECK` constraints, so an unrecognised literal would be written and silently mis-partition `idx_decisions_project_status`. `validateEnum` closes that at the service boundary: an omitted value takes the documented default (`'ACTIVE'`, `'HUMAN_CONFIRMED'`, `'warning'`), and an unrecognised one throws with the list of valid values. This is validation, not coercion — `'active'` is rejected rather than upcased, so a caller bug surfaces immediately.

**Confidence.** `clampConfidence` maps `undefined`, `NaN`, and `Infinity` to `1.0`, and clamps everything else into 0–1, matching the range documented on the shared type.

**String arrays.** `constraints` and `nonGoals` are trimmed, emptied entries dropped, deduplicated, then `JSON.stringify`d into the `_json` columns. On read, `parseStringArray` tolerates corrupt content — invalid JSON or a non-array yields `[]` rather than throwing, so one bad row cannot take down a listing.

**Required text.** `title`, `summary`, `rationale`, `goal`, `statement`, and `projectId` are trimmed and rejected when empty. A whitespace-only title is a caller bug, and the schema's `NOT NULL` does not catch it.

**Batch code-ref loading.** `listDecisions` and `findRelevantDecisions` fetch all code refs for the result set in one `IN (…)` query and group them in memory, rather than issuing one query per decision. `idx_decision_refs_decision` from P5.0-03 serves that lookup.

### `relatedFiles` — a type/schema gap, resolved by derivation

`ProjectDecision.relatedFiles: string[]` exists in the P5.0-02 shared type, but **`project_decisions` has no `related_files` column** — the P5.0-03 DDL, given verbatim in that brief, does not include one. The DDL is frozen for this task, so:

- On **read**, `relatedFiles` is derived as the distinct non-null `file_path` values of the decision's code refs.
- On **write**, a `relatedFiles` entry is persisted as a file-only row in `decision_code_refs`. A path already anchored by an explicit `codeRefs` entry is skipped, so it is never stored twice.

This keeps the field durable and round-trippable, and it makes `findRelevantDecisions` match on paths supplied either way. The cost is that `relatedFiles` and `codeRefs` are no longer independent: reading back a decision shows a synthetic code ref for every related file. See § 5 item 1 for the fix.

## 5. Remaining issues and questions

**1. `ProjectDecision.relatedFiles` has no column — currently derived from code refs.** This is the one genuine contradiction between the P5.0-02 type and the P5.0-03 schema. The derivation described in § 2 keeps behaviour correct, but it conflates two concepts: after a round-trip, `codeRefs` contains a synthetic entry for every related file. If `relatedFiles` is meant to be independent (files a decision governs, whether or not a symbol is anchored there), add `related_files_json TEXT NOT NULL DEFAULT '[]'` through the existing idempotent `ALTER TABLE … ADD COLUMN` pattern and switch the mapper. That is a small change now and a data migration later. **This needs a decision before P5.0-07 exposes the field over REST.**

**2. `scope_pattern` default is still `'*'` in the schema and `'**'` in the shared type's doc comment.** Carried forward unresolved from P5.0-03 § 5. The service defaults to `'*'` to match the schema — one source of truth, chosen so the value in the database is the value the service writes. The doc comment in `packages/shared/src/types/memory.ts` should be corrected, or the schema default changed, before P5.0-05 implements rule matching. In glob semantics `*` does not cross path separators, so a matcher taking the type comment at face value would apply project-wide rules to top-level files only.

**3. `ORDER BY created_at DESC` is non-deterministic within a millisecond.** `created_at` is `Date.now()`, and several decisions created in the same tick — entirely plausible from a batched agent write or a REST loop — tie, leaving SQLite free to return them in any order. The tests work around it with a busy-wait. The durable fix is a secondary sort key (`ORDER BY created_at DESC, id DESC`) on `listDecisions`, `listRules`, `getActiveIntent`, and `findRelevantDecisions`. I did not add it because the brief specified the ordering clause exactly; it is a one-line change per query if you want it.

**4. Enum validation is service-level only.** Anything writing SQL directly — a future migration, a repair script, a P5.0-05 lifecycle path that bypasses these methods — can still insert `'active'`. The schema-level fix (`CHECK` constraints) remains available only until rows exist, since SQLite cannot add a `CHECK` via `ALTER TABLE`.

**5. `transaction()` is not re-entrant.** SQLite has no nested `BEGIN`, so calling `createDecision` from inside another transaction throws. P5.0-05's supersede flow will want to archive the old decision and create the replacement atomically — it should either use savepoints or compose the SQL directly rather than nesting these methods.

**6. `updatedAt` is never advanced after creation.** No method mutates a decision or rule, so `updated_at` always equals `created_at` except on an archived intent. That is correct for this task's scope and will change in P5.0-05.

**7. The Blueprint still has no Project Memory entry.** Unresolved across P5.0-01 (§ 5.7), P5.0-02 (§ 4.1), and P5.0-03 (§ 5.6). There is now a schema and a service implementing a subsystem that the normative specification does not describe, in a repository whose `CLAUDE.md` states the Blueprint governs and that changes to it require a Change Proposal. Each task makes this more expensive to reconcile.

**8. CI is still red on `main`** — 38 pre-existing lint errors in files untouched by this work (P5.0-03 § 3). Every "build passes" claim in this series is verified locally; the pipeline itself provides no signal.
