## 2. Implementation

### `getProjectBriefing(projectId)`

Five reads, assembled into the `ProjectBriefing` shape defined in P5.0-02:

| Field | Source |
| :-- | :-- |
| `activeDecisions` | `this.listDecisions(projectId, { status: 'ACTIVE' })` |
| `architecturalRules` | `this.listRules(projectId)` |
| `currentIntent` | `this.getActiveIntent(projectId)` |
| `recentAgentWork` | `sessions`, aliased, `ORDER BY started_at DESC, id DESC LIMIT 5` |
| `recentApprovals` | `approvals`, aliased, `ORDER BY created_at DESC, id DESC LIMIT 5` |

The first three reuse the existing methods rather than duplicating SQL, so they inherit the deterministic sort keys added in P5.0-05, the code-ref batch loading from P5.0-04, and the corrupt-JSON tolerance in `parseStringArray`. The two new queries follow the aliasing the brief specifies (`id AS sessionId`, `action_id AS actionId`, …) and are served by `idx_sessions_project_started` and `idx_approvals_project_created` — the indexes added in P5.0-03 specifically for this lookup, and confirmed there by `EXPLAIN QUERY PLAN`.

**This is the design P5.0-01 verified.** No `agent_work_records` table exists or was needed: `sessions` and `approvals` already carry sufficient data, written by `AgentService` and `ApprovalManager` on every start, exit, crash, and approval gate.

### Determinism

The output depends only on database contents. There are no model calls, no sampling, no `Date.now()` in the returned value, and no iteration over an unordered structure. Every one of the five queries carries a **total** order — `id` breaks any timestamp tie — so the result is not merely deterministic in the usual case but byte-identical even when every `started_at` / `created_at` in the project is the same value. That last case is the one an ordinary determinism test misses, and it is asserted directly (§ 3).

### Row mapping

The aliased SQL returns rows that are close to, but not identical with, the domain types, so two small mappers sit between them:

- **`mapAgentWork`** — `sessions.thread_id` is nullable (added by `ALTER TABLE`, `NULL` on rows written before it existed), while `AgentWorkSummary.threadId` is an *optional*. The mapper omits the key entirely rather than setting it to `null`, so the field is absent from `JSON.stringify` output instead of serializing as `"threadId": null`. Both behaviours are asserted.
- **`mapApproval`** — projects `action_id` to `actionId`. This is the correlation key the client responds on, not the row's primary key, matching the `ApprovalSummary` contract from P5.0-02.

Both cast `status` to its domain union; see § 5 item 3.

**175 of 175 pass**, up from 119. Every requirement in the brief is covered. Six places where the tests go past the happy path:

- **The `LIMIT 5` is actually exercised.** Seven sessions and seven approvals are seeded, so the cap truncates rather than coincidentally fitting, and the exact five ids returned are asserted in order — not just the count.
- **The determinism test is not trivially satisfiable.** `run1.length > 200` guards against the failure mode where two empty briefings compare equal and the test passes vacuously.
- **Determinism is checked under total tie.** Every `started_at`, `created_at` in Project C is forced to one value, then two briefings are compared and the session order is asserted to be exactly `id DESC`. Without the secondary sort keys from P5.0-05 this is where an unstable `ORDER BY` would surface; with distinct timestamps it never would.
- **The `NULL` thread_id path is proven, not assumed.** The fixture's `NULL` is verified at the SQL level first, then the mapper output is checked for key *absence* (`'threadId' in summary === false`) and confirmed to survive `JSON.parse(JSON.stringify(...))` as `undefined` rather than `null`.
- **Object shape is asserted, not just field values.** `Object.keys(...).sort()` on the briefing, an `AgentWorkSummary`, and an `ApprovalSummary` catches accidental extra fields leaking from the row into the response — the kind of thing that becomes an API contract once P5.0-07 serializes it.
- **Isolation is asserted as a property.** Every decision and rule in the briefing is checked to carry the queried `projectId`, alongside the specific "B's session/approval does not appear in C" checks and the reverse direction.

The cascade group gained four assertions documenting a real consequence of P5.0-01 § 2 finding #4: `sessions` and `approvals` declare **no foreign key** on `project_id`, so after a project is deleted its decisions, rules, and intent are gone but its session and approval history remains, and the briefing still returns it.

## 5. Remaining issues and questions

**1. `activeDecisions` and `architecturalRules` are unbounded.** `recentAgentWork` and `recentApprovals` are capped at 5, but the decision and rule lists are not. A project that has accumulated 300 `ACTIVE` decisions — each with its full `rationale`, `constraints`, and every code ref — produces a briefing of arbitrary size. If this object is destined for an agent prompt (which is what "briefing" implies), it needs a budget: a cap, a relevance filter, or the token-aware truncation `ContextService.assembleContextWindow` already implements for context windows. **This is the item most likely to bite in P5.0-08.**

**2. `LIMIT 5` is hardcoded.** Written literally as the brief specifies. Callers cannot ask for more history, and there is no pagination. A `limit` parameter defaulting to 5 would cost one line if the REST layer needs it.

**3. `status` is cast, not validated.** `row.status as AgentWorkStatus` and `as ApprovalOutcome` assert a type the database does not enforce — the columns have no `CHECK` constraint (P5.0-03 § 5). `AgentService` and `ApprovalManager` only ever write the known literals, so this is accurate today, but the type is a claim rather than a guarantee: a legacy row or a manual `UPDATE` with an unexpected value would flow through typed as valid. The decision/rule/intent paths *do* validate on write; these two read from tables this service does not own, so a read-side normalizer is the equivalent safeguard if it matters.

**4. The five queries are not one snapshot.** They run outside a transaction, so a concurrent write between the decision query and the approvals query yields a briefing that never corresponded to any single database state. Determinism (same input → same output) holds and is tested; atomicity does not. Given the EventBus writes sessions and approvals continuously while agents run, wrapping the five reads in a transaction — the existing private `transaction()` helper would need a read-only variant, since it is currently write-shaped — would make the snapshot coherent.

**5. `recentApprovals` includes every status.** `pending`, `approved`, `denied`, and `expired` are all returned undifferentiated, and the brief specifies no filter. For an agent briefing, an unresolved `pending` approval is a materially different signal from a historical `denied` one. Worth deciding whether the briefing should separate them or the consumer should.

**6. Approvals still carry no resolution timestamp and no thread attribution.** Carried from P5.0-01 § 2: `approvals` records only `created_at`, so the briefing cannot say *when* a gate was decided, and `approvals.thread_id` is never written by `ApprovalManager`, so approvals cannot be attributed to a thread. Neither blocks this task — `ApprovalSummary` exposes neither field — but both limit how informative the briefing can be.

**7. Carried forward unresolved.** The bidirectional `supersededBy` semantics (P5.0-05 § 5 item 1) — now doubly relevant, since `activeDecisions` will surface `ACTIVE` decisions carrying a non-null `supersededBy` straight into the briefing, where the field means the opposite of its documented meaning. Also `relatedFiles` has no column (P5.0-04), `scope_pattern` is `'*'` in the schema and `'**'` in the type's doc comment (P5.0-03), and there are no `CHECK` constraints on the enum columns.

**8. The Blueprint still has no Project Memory entry, and CI is still red on `main`** (38 pre-existing lint errors, P5.0-03 § 3). Six tasks in, the subsystem now has a schema, a service, a lifecycle model, and a briefing generator, none of which the normative specification describes. Every "build passes" claim in this series is local verification, not pipeline verification.
