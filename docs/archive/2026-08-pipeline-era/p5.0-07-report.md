## 2. Implementation

### Publish sites

Four, matching the brief's envelopes exactly — `source: 'system:memory'`, `crypto.randomUUID()` id, `Date.now()` timestamp:

| Method | Event | Payload |
| :-- | :-- | :-- |
| `createDecision` | `memory.decision_created` | `{ projectId, decision }` |
| `supersedeDecision` | `memory.decision_superseded` | `{ projectId, decisionId, supersededBy, decision }` |
| `createIntent` | `memory.intent_updated` | `{ projectId, intent, previousIntentId? }` |
| `createRule` | `memory.rule_created` | `{ projectId, rule }` |

Two placement decisions matter more than the envelope shape:

**Publishing happens after the transaction commits, and after the record is read back.** The payload therefore carries the fully mapped domain object — defaults applied, JSON round-tripped, code refs attached — not an optimistic reconstruction. More importantly, a subscriber can never observe an event for a write that subsequently rolls back. Because `insertDecision` (P5.0-05) is the shared write path and it does *not* publish, `supersedeDecision` emits `memory.decision_superseded` **only** — it does not also emit `memory.decision_created` for the replacement it inserts. That is asserted directly.

**`previousIntentId` is captured before the transaction.** `createIntent` archives whichever intent was `ACTIVE`, so by the time it returns the predecessor is no longer discoverable by query. The id is read first and included only when one existed — the key is omitted, not set to `undefined`, so a project's first intent produces a payload with no `previousIntentId` at all rather than a null-ish field.

### `publishMemoryEvent()` — why publishing goes through one guarded helper

`EventBus` wraps a Node `EventEmitter`, so **dispatch is synchronous**: `eventBus.publish()` runs every subscriber on the caller's stack before returning. Two failure modes follow, and both are absorbed here rather than left to each call site:

1. **A subscriber that throws** would propagate out of `createDecision` and land on the caller as if the write had failed — when in fact it committed. The helper catches, logs, and swallows, consistent with the codebase rule that adapter and subscriber failures must never take down the Core.
2. **A subscriber that writes memory** re-enters the service on the same stack and publishes again, forever. A `publishDepth` counter caps nesting at `MAX_PUBLISH_DEPTH = 4`; past that the publish is dropped with a logged error naming the cause. The cycle terminates with a diagnostic instead of a stack overflow, and the counter unwinds in a `finally` so later publishes are unaffected.

### `initEventBusListeners()`

An idempotent registration point, guarded by a `listenersInitialised` flag — EventBus is a process-wide singleton, so a second call would otherwise stack duplicate listeners and double every reaction. It returns `true` on the call that registers and `false` afterwards.

**It registers no subscription today, deliberately.** No existing system event requires a memory write: `agent.status`, `chat.message`, `client.command`, `approval.request`, and `context.updated` all describe activity that memory observes rather than records, and deciding that, say, a crashed session should mark decisions `STALE` would be inventing product behaviour — which `CLAUDE.md` forbids without a Change Proposal. The method exists as the single seam where P5.0-08+ adds them, carrying two documented rules:

- **Never subscribe to the literal `'*'` channel.** `EventBus.publish` re-emits every event there (ADR-008), including this service's own `memory.*` events, so any handler that writes would feed itself immediately.
- **A handler that writes memory must not react to a `memory.*` type.** The depth guard bounds such a cycle, but it bounds a bug rather than licensing one.

See § 5 item 1 — this is the one part of the brief delivered as scaffolding rather than behaviour, and it is flagged rather than quietly filled with invented logic.

The two `console.error` lines in that output are **expected**: they are the guards firing under test — a deliberately throwing subscriber and a deliberately re-entrant one. They are diagnostics, not failures.

Six things the tests check that a shape-only assertion would miss:

- **Exactly one event per write**, asserted by clearing the capture buffer before each call and checking the count — this is what catches a double publish, and it is how "supersede does not also publish `decision_created`" is proven.
- **Silence is tested.** Reads (`getProjectBriefing`, `listDecisions`, `getActiveIntent`) and *rejected* writes (unknown project, unknown decision) must publish nothing. An event emitted for a write that never happened is the worst failure mode here, and it is checked explicitly for both rejection paths.
- **The throwing-subscriber path asserts the caller's contract, not just that nothing crashed:** the call does not throw, it returns a rule, and the rule is then re-read from the database to prove it really persisted.
- **The infinite-loop test is real recursion, not a mock.** A subscriber to `memory.rule_created` calls `createRule` again. Without the guard this is an unbounded synchronous cycle. The test asserts the call does not throw, that recursion was bounded well under its own 50-call safety net, and — importantly — that a *later* publish still reaches subscribers, proving the depth counter unwinds rather than latching.
- **The envelope shape is pinned** with `Object.keys(event).sort()`, so a stray field cannot leak into what becomes a wire format the moment P5.0-08 forwards these over Socket.IO.
- **Unsubscribe is verified to detach**, so the test group leaves no listeners behind to contaminate the cascade group that follows.

## 5. Remaining issues and questions

**1. `initEventBusListeners()` registers nothing.** Delivered as an idempotent, documented seam rather than as behaviour, because no existing system event has a defined memory consequence and inventing one is out of bounds. **This is the one part of the brief not delivered as working logic, and it needs a product decision**: which system events should write memory? Plausible candidates, none of them specified anywhere: `agent.status` with `status: 'crashed'` marking related decisions `STALE`; a git commit anchoring `decision_code_refs.commit_hash`; `approval.request` for a command that violates an `ArchitecturalRule` raising the gate's severity. Each is a product behaviour that belongs in a Change Proposal before code.

**2. Nothing calls `initEventBusListeners()` yet.** The service is not imported anywhere in the running server, so neither the publishes nor the init run in production. P5.0-08 must import the singleton and call it once during startup (alongside `agentService.recoverSessions()` in `index.ts`), or this integration stays dormant.

**3. Events are published, but nothing forwards them to clients.** `socketManager` broadcasts specific event types to project rooms; `memory.*` is not among them. Until P5.0-08 adds that, these events are server-internal only. Worth noting that the payloads embed full `ProjectDecision` objects with all code refs — fine on an in-process bus, potentially large over a WebSocket, and directly connected to the unbounded-briefing concern from P5.0-06 § 5 item 1.

**4. Publishing after commit means an event can be lost.** If the process dies between `COMMIT` and `publish`, the write is durable but no one is told. The alternative — publishing inside the transaction — trades that for the worse failure of announcing writes that then roll back. The current choice is the right one; the residual gap is inherent to a non-transactional bus and only matters if a subscriber ever performs a side effect that must not be missed.

**5. The depth guard is per-service-instance, not per-cycle.** `publishDepth` lives on the singleton. A cycle routed through a *second* `ProjectMemoryService` instance (the tests construct none, but nothing prevents it) would not share the counter. In practice the exported singleton is the only instance; making the counter `static` would close the hole if that changes.

**6. Carried forward unresolved.** The bidirectional `supersededBy` semantics (P5.0-05 § 5.1) — now shipped in a payload, so `memory.decision_superseded.decision.supersededBy` points at the *old* decision while the sibling `supersededBy` field points at the *new* one, in the same object. Consumers will find that confusing and it is about to reach the wire. Also: unbounded briefing size (P5.0-06 § 5.1), `relatedFiles` has no column (P5.0-04 § 5.1), `scope_pattern` `'*'` vs `'**'` (P5.0-03 § 5.3), no `CHECK` constraints on enum columns.

**7. The Blueprint still has no Project Memory entry, and CI is still red on `main`** (38 pre-existing lint errors). Seven tasks in: schema, service, lifecycle, briefing, and now an event contract — none of it described by the normative specification, on a pipeline that gives no signal.
