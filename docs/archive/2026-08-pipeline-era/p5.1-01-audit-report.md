## 2. MCP SDK: availability, version, packaging

### The lockfile hit is a red herring

`@modelcontextprotocol/sdk` **does** appear in `pnpm-lock.yaml` — but only here:

```yaml
'@google/genai@2.12.0':
  peerDependencies:
    '@modelcontextprotocol/sdk': ^1.25.2
  peerDependenciesMeta:
    '@modelcontextprotocol/sdk':
      optional: true
```

That is an **optional peer dependency of `@google/genai`**, which `apps/server` uses for the Gemini provider. No workspace package depends on the SDK, and it is **not installed**:

```
$ ls -d node_modules/.pnpm/*modelcontext*   → NOT INSTALLED
$ ls -d node_modules/@modelcontextprotocol  → not present
```

**P5.1-02 must add and install it.** The registry is reachable from this environment (verified with `npm view`), so no vendoring workaround is needed.

### Recommended versions

| Package | Version | Role |
| :-- | :-- | :-- |
| `@modelcontextprotocol/sdk` | `^1.30.0` (current latest) | MCP server + stdio transport |
| `zod` | `^4.4.3` | **Required** peer of the SDK |

`zod` is already in the pnpm store at `3.25.76` (via `chromium-bidi`/puppeteer) and `4.4.3` (via ESLint tooling), but both are **transitive**. Under pnpm's strict `node_modules` layout a workspace package cannot import an undeclared transitive dependency, so `zod` must be declared explicitly. Declaring `^4.4.3` reuses the copy already in the store rather than adding a third version.

### SDK facts that shape the package configuration

```
type:             "module"          (ESM-first, but ships CJS)
engines:          node >=18
peerDependencies: zod ^3.25 || ^4.0        (required)
                  @cfworker/json-schema    (optional — can be skipped)
exports:          "." and "./*" with both import (ESM) and require (CJS) conditions
```

Two consequences:

1. **CJS is viable.** The SDK exposes `require` conditions for every subpath, so `packages/mcp-memory-server` can stay CommonJS like the rest of the repo (`apps/server`, `packages/shared`, `packages/adapters` are all CJS; only `apps/marketing` and `packages/config-eslint` are ESM). Staying CJS is the lower-risk choice: it matches `tsconfig.base.json`, works with `tsx`, and avoids the `__dirname`/import-assertion friction that ESM would introduce.
2. **The dependency footprint is large.** The SDK pulls in `express@5`, `hono`, `cors`, `jose`, `ajv`, `eventsource`, and `express-rate-limit` as *direct dependencies*, even for a stdio-only server. They are installed but never loaded on the stdio path. Worth knowing before someone is surprised by the package's install size; it is not a blocker.

### Packaging shape

`pnpm-workspace.yaml` globs `packages/*`, so a new directory is picked up with no config change, and `turbo.json` defines `build`/`lint`/`clean` globally rather than per package — the new package inherits the pipeline automatically.

The monorepo convention for libraries is **ship raw TypeScript**: both `@asterim/shared` and `@asterim/adapters` set `"main": "src/index.ts"` and let the consumer's bundler transpile. An MCP server is not a library, though — it is an executable that Claude Code spawns. It therefore needs the `apps/server` treatment instead: a `bin` entry pointing at a built artifact (`apps/server` uses `"bin": { "asterim": "./dist/index.js" }` with a `#!/usr/bin/env node` banner injected by `tsup`).

**Recommendation:** mirror `apps/server` — `tsup` to CJS with a shebang banner, `bin: { "asterim-mcp-memory": "./dist/index.js" }`, `node-pty`-free, and `node:sqlite` marked `external`.

## 3. Service re-use architecture

### The dependency closure is clean — verified

This was the primary risk going in, and it checks out. The full import closure of `ProjectMemoryService`:

```
ProjectMemoryService.ts
  ├── crypto                    (node builtin)
  ├── DatabaseService.ts
  │     ├── node:sqlite         (node builtin)
  │     └── path, os, fs        (node builtins)
  ├── EventBus.ts
  │     ├── events              (node builtin)
  │     └── @asterim/shared     (types only at runtime)
  └── @asterim/shared           (type-only import)
```

**No Fastify, no Socket.IO, no controllers, no middleware.** Importing `ProjectMemoryService` boots exactly one thing: the SQLite connection. The in-process design in the task plan is sound.

### How to reach the service — three options, evaluated

**Option A — move the services into `@asterim/shared`. Ruled out.**
`@asterim/shared` is a dependency of `apps/web` (`"@asterim/shared": "workspace:*"`), which is a **browser** Vite bundle importing it from `useSocket.ts`, `useWorkstations.ts`, `useThreadContext.ts` and more. Adding `node:sqlite`, `fs`, and `os` to that package would break the web build. `CLAUDE.md` also scopes it explicitly as "the contract across the WebSocket boundary". Do not put database code there.

**Option B — depend on the `asterim` workspace package and deep-import.**
`packages/mcp-memory-server` declares `"asterim": "workspace:*"`, pnpm symlinks `node_modules/asterim → apps/server`, and the MCP entry imports `asterim/src/services/ProjectMemoryService`. This resolves and requires no refactor.

The catch: `apps/server`'s `"main"` is `./dist/index.js`, which is the **bundled server that constructs Fastify and calls `listen()`**. There is no `exports` map, and `tsup` bundles only `src/index.ts`, so `dist/` contains no separately importable service. The deep path therefore reaches past the package's public surface into its source tree — it works, but it is coupling that no manifest documents and that a future `exports` field would silently break.

**Option C — extract a `packages/memory-core` workspace package. Recommended.**
Move `DatabaseService.ts`, `EventBus.ts`, and `ProjectMemoryService.ts` into a new package with `"main": "src/index.ts"`, matching the `@asterim/shared` / `@asterim/adapters` convention. Both `apps/server` and `packages/mcp-memory-server` then consume a real, declared public API.

Cost: three files move and roughly a dozen import sites in `apps/server` update (`AgentService`, `ApprovalManager`, `ContextRepository`, `socketManager`, routes, `index.ts` all import `dbService` or `eventBus`). It is mechanical, and `pnpm run build` plus the 365 Phase 5.0 assertions would catch any mistake immediately.

**Judgement:** Option C is the correct architecture and the refactor is well-covered by existing tests, but it is a change to `apps/server` and therefore a scoping decision for whoever owns P5.1-02 — not something to slip in silently. If P5.1-02 must stay narrow, Option B is acceptable **provided the coupling is written down** in the package README and in `IMPLEMENTATION_DRIFT.md`, because it is exactly the kind of undocumented reach-through that breaks a year later.

### Two behaviours the MCP entrypoint must respect

1. **`DatabaseService` is a singleton constructed at import time** (`export const dbService = new DatabaseService()`), and it resolves `ASTERIM_DATA_DIR` in that constructor. Any override must be set **before** the first import — the same hoisting constraint the Phase 5.0 test suites work around with `require` instead of `import`.
2. **The EventBus in the MCP process is a different EventBus.** The MCP server is a separate OS process from the Asterim server, so the four `memory.*` events it publishes go to its own in-process emitter and reach nobody. **A decision recorded through MCP will not live-update a connected dashboard**; it will only appear on the next read. That is acceptable for Phase 5.1 but should be stated rather than discovered. (It compounds `IMPLEMENTATION_DRIFT.md` § 7, where `memory.*` is not forwarded over Socket.IO even in-process.)

### Concurrency

WAL was enabled in P5.0-03 and the live database is confirmed `journal_mode=wal`, so a running Asterim server and one or more MCP processes can read concurrently while one writes. This is the configuration the task plan assumes, and it is already in place.

## 4. Stdio protocol safety

### The risk is real, and it fires before your code runs

Demonstrated empirically, capturing **stdout only**:

```
$ ASTERIM_DATA_DIR=$T tsx -e "require('./src/services/ProjectMemoryService')" 2>/dev/null
stdout bytes: 61
stdout content: [[Database] Using database at: /tmp/tmp.mO2BoXsVBb/asterim.db]
```

61 bytes of non-JSON on stdout, emitted from `DatabaseService.ts:34` **inside the singleton constructor** — i.e. as a side effect of the import itself, before a single line of MCP server code executes. Over stdio transport this corrupts the first JSON-RPC frame and the client drops the connection.

### Ordering is the trap

```
$ tsx -e "console.log = (...a) => console.error(...a); require('...')"   → stdout: 0 bytes  ✅
$ tsx -e "require('...'); console.log = (...a) => console.error(...a)"   → stdout: 61 bytes ❌
```

The guard only works if it is installed **before** the import. With TypeScript/ESM `import` statements this is not achievable by ordering source lines — imports hoist above all statements. The entrypoint must therefore either:

- use a **separate guard module imported first** (`import './stdio-guard';` before any service import — side-effect imports still hoist, but they hoist *in order*, so a guard module listed first runs first), or
- use **`require()`** for the service modules after the guard, mirroring the pattern the Phase 5.0 test suites already use for `ASTERIM_DATA_DIR`.

### What to redirect

Only `console.log` is currently dangerous in the closure:

| Call site | Stream | Risk |
| :-- | :-- | :-- |
| `DatabaseService.ts:34` `console.log` | **stdout** | **corrupts JSON-RPC** |
| `DatabaseService.ts:46` `console.warn` | stderr | safe |
| `ProjectMemoryService.ts:565,582` `console.error` | stderr | safe |

But patching `console.log` alone is fragile — Node also routes `console.info`, `console.debug`, `console.dir`, `console.table`, and `console.group` to stdout, and any future line added to these services could use one of them.

**Recommended guard** — one line, covers every console method permanently:

```ts
// stdio-guard.ts — must be the first import in the MCP entrypoint.
globalThis.console = new console.Console(process.stderr, process.stderr);
```

This rebinds the entire console to stderr, so no present or future `console.*` call in any imported module can reach stdout. For defence in depth, P5.1-02 may additionally wrap `process.stdout.write` to drop anything that is not written by the transport, but the console rebind is the necessary and sufficient fix for the failure mode identified in the task plan (§ 6.1).

## 5. Project identity resolution

### `ProjectManager` cannot look up by path

Audited in full. The available queries are:

| Method | Query |
| :-- | :-- |
| `getProject(id)` | `SELECT … FROM projects WHERE id = ?` |
| `getProjects(workspaceId?)` | `SELECT … FROM projects ORDER BY created_at DESC` (+ workspace filter) |
| `addProject`, `removeProject`, `getThreads`, `createThread` | — |

**There is no `getProjectByPath`.** `path` is only ever selected as an output column, never used in a `WHERE` clause. P5.1-03 must therefore either add such a method to `ProjectManager` (touches `apps/server`) or have the resolver run its own `SELECT id, path FROM projects` and match in memory. Given that correct matching needs normalization and longest-prefix logic anyway (below), **in-memory matching inside the resolver is the better fit** — the logic belongs to the resolver, not to `ProjectManager`.

### The live data makes a naive implementation fail

Read from the real `~/.asterim/asterim.db`:

```json
{"name":"MainTest",  "path":"/home/qhukz/Documents/Projects/"}
{"name":"test",      "path":"/home/qhukz/Documents/Projects/AgentDeckTEST"}
{"name":"Asterim",   "path":"/home/qhukz/Documents/Projects/Asterim"}
```

Four concrete hazards, all present in this database today:

1. **Trailing slashes are not normalized on write.** `MainTest` is stored as `…/Projects/`. `process.cwd()` never has a trailing slash, so an exact string match can never resolve that project. **Normalize both sides** (`path.resolve()` strips it).
2. **One project is an ancestor of another.** cwd `/home/qhukz/Documents/Projects/Asterim` matches `Asterim` exactly *and* `MainTest` by ancestor traversal. A resolver that walks up from cwd and returns the first hit may return `MainTest` depending on iteration order. **Always choose the longest matching path**, which is the most specific project.
3. **Prefix matching without a separator boundary is wrong.** `startsWith('/home/qhukz/Documents/Projects/Asterim')` would also match a sibling `…/AsterimOld`. **Compare resolved segments** (e.g. `path.relative(projectPath, cwd)` must not start with `..` and must not be absolute) rather than raw string prefixes.
4. **Stored paths may not exist on disk.** `AgentDeckTEST` reflects the project's pre-rename era. The resolver **must not** require `fs.existsSync(project.path)` — a stale row should still resolve if cwd is inside it.

Note also that `MainTest` points at `/home/qhukz/Documents/Projects/` — a directory containing *all* the user's projects. Any cwd under it resolves to something. That makes hazard 2 not a corner case but the default experience on this machine.

### Recommended algorithm for P5.1-03

```
1. --project <id>              → getProject(id); fail loudly if unknown
2. --project-path <path>       → resolve, then match as in step 4
3. ASTERIM_PROJECT_ID          → getProject(id); fail loudly if unknown
4. CWD auto-detection:
     cwd := path.resolve(process.cwd())
     candidates := all projects where path.resolve(p.path) === cwd
                   OR cwd is inside path.resolve(p.path)   [segment-safe containment]
     pick the candidate with the longest resolved path
5. No match → fail with an actionable message listing known project paths,
   never silently default to "the first project"
```

Step 5 matters: silently picking a project would let an agent write a decision into the wrong project's memory, which Phase 5.0 spent considerable effort making impossible at every other layer.

The task plan's mitigation (§ 6.2) also mentions git-repo-root traversal. That is a reasonable *fallback* after step 4 fails, but it must not outrank an exact match — a monorepo has one git root and many potential projects.

## 7. Architectural blockers

**None that block P5.1-02.** Five items require a decision, and one is a correctness trap rather than a choice:

| # | Item | Type | Owner |
| :-- | :-- | :-- | :-- |
| 1 | Service re-use: extract `packages/memory-core` (Option C) vs deep-import `asterim` (Option B) | Scoping decision | P5.1-02 |

| 3 | CWD resolution must normalize, use segment-safe containment, and prefer the longest match | Correctness trap | P5.1-03 |
| 4 | MCP-published `memory.*` events reach no dashboard (separate process) | Known limitation | Document in P5.1-08 |
| 5 | `engines.node` should be `>=22` for `node:sqlite` | Manifest detail | P5.1-02 |

Items 2 and 3 are the ones that produce silent, hard-to-diagnose failures: a corrupted JSON-RPC stream looks like a broken MCP client, and a mis-resolved project writes correct data into the wrong project.
