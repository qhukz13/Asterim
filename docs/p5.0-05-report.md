`getActiveIntent` deserves a note: `LIMIT 1` over a tie previously made *which* intent counts as current a coin flip. It is now stable.

### `insertDecision` — the composability fix

P5.0-04 § 5 item 5 flagged that `transaction()` is not re-entrant, so `supersedeDecision` could not simply call `createDecision`. Rather than nest transactions or duplicate the insert logic, the validate-and-write body was extracted into a private `insertDecision(params): string` that issues **no** `BEGIN` of its own:

- `createDecision` = `transaction(() => insertDecision(params))`
- `supersedeDecision` = `transaction(() => { insertDecision(...); update old; update new })`

Validation, defaulting, clamping, code-ref merging, and `relatedFiles` derivation are therefore identical on both paths — a decision created by superseding is indistinguishable from one created directly. `createDecision`'s public behaviour is unchanged; its P5.0-04 tests still pass untouched.

### Lifecycle methods

**`supersedeDecision(oldDecisionId, newParams)`** — reads the old decision and throws if absent; compares `oldDecision.projectId` against `newParams.projectId` and throws on a mismatch, quoting both ids. Both checks run **before** the transaction opens, so a rejected call performs no writes at all. Inside one transaction it inserts the replacement with `status` forced to `'ACTIVE'` (a caller-supplied status is overridden, not honoured — the replacement is by definition the decision now in force), stamps `status='SUPERSEDED'`, `superseded_by=<new id>`, `updated_at` on the old row, and writes the back-link `superseded_by=<old id>` on the new row. Returns the replacement read back with its code refs.

**`archiveDecision(id)`** — delegates to `updateDecisionStatus(id, 'ARCHIVED')`. One code path for status changes means one place where `updated_at` is stamped and one place where existence is checked.

**`updateDecisionStatus(id, status)`** — validates the status against `DECISION_STATUSES` via the existing `validateEnum` (throws on anything outside the union, since the column still has no `CHECK` constraint), verifies the decision exists, updates `status` and `updated_at`, and returns the re-read record.

All three read the row back after writing rather than returning a constructed object, matching the P5.0-04 convention: the caller sees what is actually in the database.

## 5. Remaining issues and questions

**1. The bidirectional `superseded_by` link contradicts the field's documented meaning.** `packages/shared/src/types/memory.ts` documents `supersededBy` as *"Id of the decision that replaced this one; `null` unless `status` is `'SUPERSEDED'`."* After a supersede, the **`ACTIVE` replacement carries a non-null `supersededBy`** pointing at the decision it replaced. The column now means two opposite things depending on the row's status: on a `SUPERSEDED` row it is "replaced by", on an `ACTIVE` row it is "replaces". Implemented exactly as the brief specifies, but a consumer cannot interpret the field without also reading `status`, and P5.0-07 is about to expose it over REST. The clean fix is a separate `supersedes` field (a second column, or a derived reverse lookup `SELECT id WHERE superseded_by = ?`), leaving `supersededBy` unidirectional. **Worth resolving before the REST surface freezes.**

**2. The back-link is not durable across a chain.** Supersede A→B then B→C: the second call overwrites `B.superseded_by` from `A` to `C`. B's record of what it replaced is gone. The forward chain survives (`A.superseded_by = B`, `B.superseded_by = C`), so history is still traversable in one direction, but the back-link is only ever accurate for the most recent replacement. This is an unavoidable consequence of storing two relationships in one column — it disappears if item 1 is resolved.

**3. `updateDecisionStatus` can create an inconsistent SUPERSEDED row.** Calling it with `'SUPERSEDED'` sets the status while leaving `superseded_by` `NULL` — a decision marked as replaced by nothing. The brief specifies the method validates only against the union, so no guard was added. Options: reject `'SUPERSEDED'` from this method and require `supersedeDecision`, or clear/require the link explicitly. Related: the method permits any transition, including `ARCHIVED → ACTIVE` (tested and passing) — fine if resurrection is intended, worth a guard if not.

**4. `relatedFiles` still has no column** — carried unresolved from P5.0-04 § 5 item 1. Superseding inherits the derivation: the replacement's `relatedFiles` comes from its own code refs, which is correct, but the underlying conflation of `relatedFiles` and `codeRefs` is unchanged. Still the item most worth deciding before P5.0-07.

**5. `scope_pattern` is still `'*'` in the schema and `'**'` in the shared type's doc comment** — carried from P5.0-03 § 5 item 2 and P5.0-04 § 5 item 2. Untouched here because no rule-matching logic was in scope, but P5.0-06's briefing will likely be the first consumer that has to decide what the pattern means.

**6. `transaction()` remains non-re-entrant** — by design. `insertDecision` is now the composable unit for anything that needs to write a decision inside a larger transaction; the public `createDecision` and `supersedeDecision` must still not be called from within another transaction. Anything added in P5.0-06+ that batches writes should compose `insertDecision`, not the public methods.

**7. No `CHECK` constraints on the enum columns** — carried from P5.0-03. Service-level validation now covers three write paths (`insertDecision`, `updateDecisionStatus`, `createRule`), but direct SQL still bypasses it, and SQLite cannot add a `CHECK` via `ALTER TABLE` once rows exist.

**8. The Blueprint still has no Project Memory entry**, and **CI is still red on `main`** (38 pre-existing lint errors, P5.0-03 § 3). Five tasks in, a schema, a service, and a lifecycle model now exist for a subsystem the normative specification does not describe, on a pipeline that provides no signal. Every "build passes" claim in this series is a local verification.
